# Verification Trust Boundary

## Status

Accepted.

## Context

Superoptimization, stochastic search, GPU kernels, learned heuristics, and
complex layout solvers can be large and difficult to trust. Treating the same
optimizer that proposes a transformation as the authority that declares it
correct would make optimization bugs semantic bugs.

## Decision

Optimization is untrusted; deterministic verification owns acceptance.

Compiler stages preserve enough semantic evidence for differential testing,
translation validation, static analysis, and proof-producing lowering where
practical. Candidate code generated by CPU, CUDA, PyTorch-guided, stochastic,
learned, or future algorithms is admitted only after an independent trusted
check.

The historical oracle, independent modern VMs, bounded/exhaustive tests, and
small checkers form overlapping evidence sources rather than one monolithic
trusted optimizer.

## Alternatives Considered

### Trust production optimizer tests alone

Rejected because tests cannot establish arbitrary candidate equivalence and
heuristic search creates a large adversarial state space.

### Formally verify every optimizer implementation

Rejected as an initial requirement because it would make experimentation
prohibitively expensive. Verifying outputs through smaller trusted contracts is
a better research boundary.

## Consequences

- Performance components can evolve rapidly without gaining semantic authority.
- Verification cost is an explicit benchmark dimension.
- A verifier rejection is a normal candidate outcome, not a reason to relax the
  verifier.

## Implementation Notes

Verification modes must identify bounded assumptions. A bounded result must not
be presented as an unbounded proof.
